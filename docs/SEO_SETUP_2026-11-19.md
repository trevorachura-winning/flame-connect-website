# Flame Connect | SEO setup and launch checklist

**Prepared:** 19 November 2026  
**Canonical website:** https://www.flameconnect.tech  
**Market:** Uganda first, serving African organisations.  
**Website-only release:** No public login, contact API or integrated SaaS checkout.

## 1. Technical SEO configured in code

- `lib/seo.ts` supplies page-specific titles, descriptions, canonical www URLs, Open Graph and X/Twitter card metadata; article shares include their actual publication dates.
- The main corporate identity in JSON-LD is `Organization` with the original 512x512 Flame mark as its logo, verified Kampala/Uganda location and approved public email; `WebSite` references the same organization `@id`. No invented ratings, office street address or phone number.
- Bread crumbs are generated by the existing `Breadcrumbs` component and each resource article exposes `Article` structured data.
- `app/sitemap.ts` uses the central route registry. It deliberately omits `lastModified` because the CMS/content registry has no verified per-page last-update field. Article publishing dates remain in Article markup; publishing is **not** automatically the same thing as content last-modified.
- `app/robots.ts` publishes `https://www.flameconnect.tech/sitemap.xml`.
- `app/opengraph-image.tsx` provides the branded 1200x630 visual for shared links; individual page metadata references it.
- The temporary Coming Soon HTML and the production-domain rewrite response use `noindex` **only before 20 November 2026, 12:00 EAT**. Production middleware returns `NextResponse.next()` at or after the scheduled launch, so the final site is allowed to be indexed. Direct visits to `/coming-soon/index.html` remain noindex.

**Risk/mitigation:** Avoid blocking pages with `Disallow` in robots.txt during this short launch gate; a search crawler must be allowed to read `noindex`. Indexing after launch is not instantaneous, and search engines choose when to recrawl.

## 3. Search Console account actions (requires verified domain owner)

1. Sign into **https://search.google.com/search-console** with the Flame Connect Google account.
2. Add a **Domain** property: `flameconnect.tech`, so www and the apex are included.
3. Obtain Google's **unique DNS TXT verification record**. Add **that exact generated record** to the authoritative DNS provider for `flameconnect.tech`. Do not replace A/CNAME/NS records that point the website to Vercel and do not invent verification strings.
4. Verify the domain property in Search Console. This cannot be established simply by putting code in GitHub, nor should the TXT token be fabricated.
5. **After the Coming Soon gate opens and final-site QA passes**, submit sitemap: `https://www.flameconnect.tech/sitemap.xml`.
6. Use **URL Inspection** to test `https://www.flameconnect.tech/`, `/services/ai-in-business`, `/products/flame-os` and `/resources`. Request indexing only after the `noindex` header and Coming Soon page are gone from those URLs.
7. Check **Pages**, **Sitemaps**, **Search results**, and **Core Web Vitals** over the following days/weeks; Google indexing and ranking are not guaranteed.

Helpful official instructions:
- Search Console verification: https://support.google.com/webmasters/answer/9008080
- Submit a sitemap: https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap
- Organization structured data: https://developers.google.com/search/docs/appearance/structured-data/organization
- Noindex: https://developers.google.com/search/docs/crawling-indexing/block-indexing

## 4. Technical acceptance after launch

1. Check live GET/HTTP response for `/`, `/services`, all three service pages, `/products`, Flame OS/Academy pages, `/resources` and article URLs. Each public indexable page must serve genuine content, not a Coming Soon rewrite.
2. Confirm there is **no** `noindex` response header on launched corporate pages. Keep `/coming-soon/index.html` itself non-indexable.
3. Verify canonical `https://www.flameconnect.tech/...` (no apex, no duplicate slash, no Vercel preview host), unique title and description, OG URL/image, Twitter card, article date and valid JSON-LD.
4. Inspect `/sitemap.xml` and `/robots.txt`. Sitemaps should contain *indexable canonical content routes*, not discontinued product slugs or preview URLs.
5. Test browser/mobile real-device performance and accessibility. Review Core Web Vitals before compressing hero imagery or changing approved visuals.
6. Validate structured data in Google's Rich Results Test; correct errors without adding misleading or unsupported schema.
7. Preserve the website-only contact model: mailto and WhatsApp handoff, no server-side claims of form submission.
